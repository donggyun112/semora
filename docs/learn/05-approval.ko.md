# 5. 승인을 기다리고 다시 시작하기

[목차](README.ko.md) · [이전](04-controls.ko.md)

## await로 사용자 답변을 기다려도 되지 않을까?

단일 프로세스에서 짧게 기다리는 기능이라면 가능하다.
예를 들어 도구 안에서 이벤트나 큐를 기다리고 답이 오면 다음 줄을 실행할 수 있다.

다만 `await`는 현재 코루틴의 실행을 양보하는 것이지, 함수의 지역 변수와 대기 상태를 영구 저장하는 기능은 아니다.
서버를 재시작하면 메모리에 있던 대기를 그대로 이어갈 수 없다.

Semora의 승인 보류는 필요한 상태를 저장소에 보관하고 **현재 실행 시도를 끝내서 워커를 놓아주는 방식**이다.
외부 응답이 오면 저장된 정보로 새로운 실행 시도를 시작한다.

## 이번에는 의도적으로 멈춘 것이다

```text
도구 호출 요청
  → pre_tool_use에서 Suspend
  → 어떤 호출이 어떤 승인을 기다리는지 기록
  → 현재 시도 종료, 실행 점유 해제

시간 경과

승인 요청 ID와 답변 도착
  → resume
  → 현재 정책으로 재검사
  → 허용하면 도구 실행
```

이때 아직 시작하지 않은 도구에 대한 승인 대기와, 실행 도중 죽어서 결과를 모르는 상태는 다르다.
후자는 다음 장의 복구 문제다.

## 무엇을 기억해야 할까?

승인 화면의 질문 문자열만 저장해서는 부족하다.

| 정보 | 필요한 이유 |
|---|---|
| branch ID | 어느 작업을 이어갈지 식별 |
| 도구 이름·인자·호출 ID | 정확히 어떤 호출이 보류되었는지 식별 |
| pending ID | 외부 답변을 승인 요청에 연결 |
| 메시지 이력과 같은 라운드의 결과 | 모델과 도구의 대화를 이어가기 |
| 보류 당시 정책 버전 | 현재 정책과 비교할 재료 |
| 이미 수신한 답변 | 여러 승인 요청을 함께 처리 |

현재 구현의 보관 구조는 [runtime.py](../../packages/semora/src/semora/runtime.py)의 `_park`에서 볼 수 있다.
실제 프로세스 재시작을 견디려면 이 기록을 보존하는 저장소가 필요하다. `MemorySteps`는 학습용이다.

## API에서 보류를 받는 두 방식

| 인터페이스 | 보류를 알리는 방식 |
|---|---|
| `AgentRuntime.run(...)` | `AgentSuspended` 예외 |
| `semora.Agent` 인스턴스의 `run(...)` | `suspended=True`인 `Outcome` |

`permissions.py`에서 예외 처리 없이 `parked.suspended`를 검사하는 이유는 두 번째 인터페이스를 사용하기 때문이다.
같은 보류를 표현하는 모양이 다르다. 계약은 [API 문서](../API.md#runtime)에 있다.

## “승인했으면 실행”으로 끝나지 않는 이유

다음 상황을 생각해 보자.

```text
10:00  규칙 v1: 사람의 승인 후 문서 수정 허용
10:05  사용자에게 승인 요청 표시
10:10  규칙 v2: 문서가 잠겨 수정 불가
10:15  사용자가 예전 요청에서 승인 클릭
```

사용자가 승인한 사실과 현재 수정 가능한지는 다른 질문이다.
`on_resume`는 사람의 답변과 정책 버전 정보를 받아 다시 판단할 기회를 제공한다.

다음은 정책 부분 코드다.

```python
async def recheck(ctx, call, resume):
    if resume.current_rules_version == "v2-locked":
        return Deny("현재 문서는 잠겨 있습니다")
    return Continue()
```

이 함수는 버전 문자열로 판단하는 학습용 예다. 실제 애플리케이션에서는 현재 권한·문서 상태 등을 확인할 수 있다.
Semora가 버전 이름을 해석하거나 최신 정책을 다운로드해 주지는 않는다.
호스트가 재개 시점의 정책과 데이터를 공급해야 한다.

또한 `pre_tool_use`에 적은 검사가 자동으로 전부 다시 실행되는 것은 아니다.
재개 시 필요한 검사를 `on_resume`에 연결해야 한다. `ControlPlane`의 기본 `on_resume`는 승인 입력에 대해 `Continue`를 반환한다.

## 사용자가 거절한 경우는 별도로 보자

```text
승인: {"type": "approve"}
거절: {"type": "error", "message": "진행하지 마세요"}
```

현재 Semora에서는 사람의 거절을 `on_resume`로 다시 허용하게 하지 않는다.
거절된 호출의 결과는 기록하지만, 해당 라운드 뒤에 모델을 다시 호출하지 않고 `stop_reason="aborted"`로 끝낸다.

반면 `pre_tool_use`의 `Deny`는 정책 거절 결과를 모델에 주고 다른 대응을 할 수 있게 한다.
두 동작을 같은 “거절”이라고 뭉뚱그리지 말자.

한 라운드에 여러 승인이 있다면 모든 답변이 모일 때까지 보류한다.
그중 하나가 거절되어도 다른 승인된 호출은 재개 정책에 따라 실행될 수 있다. “하나 거절하면 승인된 호출까지 모두 취소”는 아니다.

## deps나 Application은 자동으로 살아나는가?

아니다. 실행 기록을 저장한다고 임의의 Python 객체, DB 연결, HTTP request가 모두 직렬화되는 것은 아니다.
새 프로세스에서 재개하려면 호스트가 필요한 서비스와 사용자 정보를 다시 구성해야 한다.

따라서 이전 장에서 사용한 요청 객체를 그대로 오래 보관하기보다, 어떤 식별자와 상태로 재개에 필요한 정보를 복원할지 생각하게 된다.
이 부분도 애플리케이션 설계에 속한다.

## 테스트로 읽기

[test_hitl.py](../../tests/test_hitl.py)의 다음 테스트를 순서대로 본다.

1. `test_the_gate_suspends_instead_of_blocking_on_an_answer`: 보류 후 도구가 실행되지 않았는가?
2. `test_resume_revalidates_the_latest_policy_before_the_effect`: 승인했지만 변경된 정책으로 실행이 막히는가?
3. `test_a_refusal_ends_the_run_without_asking_the_model_again`: 사람의 거절 뒤 모델 재호출이 없는가?

이 파일의 메모리 저장소 테스트는 객체 재생성과 제어 흐름을 검증한다.
테스트 이름에 process가 있어도 실제 PostgreSQL의 프로세스 간 내구성을 검증한 것으로 읽으면 안 된다.

## 확인 질문

**Q. 규칙 버전이 달라지면 Semora가 자동으로 거절하는가?**

아니다. 버전은 판단 재료다. 실제 판단은 호스트가 제공하는 정책이 한다.

**Q. resume는 예전 코루틴을 메모리에서 깨우는 것인가?**

아니다. 저장된 재개 정보를 사용해 새 실행 시도를 진행한다.

**Q. 사람의 승인만 받으면 권한 검사는 생략해도 되는가?**

애플리케이션이 현재 권한을 검사해야 한다면 재개 시에도 그 검사를 연결해야 한다.
